━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHAT IT DOES:
This is the main server application. It does TWO main jobs:
1. Serves the frontend files (HTML, CSS, JS) to the browser
2. Handles API requests from the frontend (get tasks, create task, etc.)

WHY IT'S IMPORTANT:
This file is like a restaurant - it serves food (frontend files) AND takes 
orders (API requests). It's the bridge between user and data.

KEY PARTS TO EXPLAIN:

1) SERVING FRONTEND FILES:
   -------------------------
   When user types "localhost:8080" in browser, this code sends the HTML:

   CROW_ROUTE(app, "/")
   - This means: "When someone visits the root URL (/), do this..."
   - Opens frontend/index.html file
   - Reads all content
   - Sends it to browser with "Content-Type: text/html" header

   Same for CSS and JavaScript files!

2) API ENDPOINTS (Routes):
   -------------------------
   These are like different counters in a restaurant:

   a) GET /api/tasks
      - When: User opens the app
      - Does: Retrieves all tasks from task_service
      - Returns: JSON array of tasks
      - Example response: [{"id":"abc123", "title":"Buy groceries", ...}]

   b) POST /api/tasks
      - When: User clicks "Save Task" in the form
      - Does: Creates new task with data from form
      - Returns: The newly created task with generated ID
      - Example: User types "Study C++" → Server saves it → Returns ID

   c) PUT /api/tasks/<id>
      - When: User edits an existing task
      - Does: Updates that specific task
      - Example: Change "Study C++" to "Study C++ pointers"

   d) DELETE /api/tasks/<id>
      - When: User deletes a task
      - Does: Removes it permanently
      - Example: Delete task with ID "abc123"

   e) POST /api/tasks/<id>/toggle
      - When: User clicks checkbox to mark task complete/incomplete
      - Does: Flips the "completed" status
      - Example: Pending → Completed (or vice versa)

   f) GET /api/stats
      - When: Dashboard loads
      - Does: Calculates total, pending, completed counts
      - Returns: {"total": 12, "completed": 3, "pending": 9, ...}

   g) GET /api/stats/weekly
      - When: Charts section loads
      - Does: Counts tasks completed in last 7 days
      - Returns: Data for bar chart

   h) GET /api/stats/categories
      - When: Charts section loads
      - Does: Counts tasks in each category
      - Returns: Data for pie chart

3) CORS HEADERS:
   -------------
   Every response includes: "Access-Control-Allow-Origin: *"
   
   WHY? Because browser security normally blocks requests between different
   origins. This header says "Allow anyone to access this API."
   
   In our case, we serve frontend from same server, so no CORS issues!

4) ERROR HANDLING:
   ---------------
   try-catch blocks everywhere:
   - If something fails (file not found, invalid data), server sends error
   - Example: Missing title → Returns 400 error "Title is required"

WHAT IT DOES:
This file contains the BUSINESS LOGIC - the actual work of managing tasks.
It's separated from main.cpp to keep code organized.

THINK OF IT AS: The kitchen in a restaurant
- main.cpp takes orders (HTTP requests)
- task_service.cpp cooks the food (processes data)

KEY FUNCTIONS:

1) create_task(Task task)
   - Generates random unique ID (like "a8f3d9e2")
   - Sets creation timestamp
   - Adds task to internal list
   - Saves to JSON file
   - Returns the created task with ID

2) get_all_tasks()
   - Simply returns all tasks in memory
   - Used when dashboard loads

3) get_task_by_id(string id)
   - Searches for specific task by ID
   - Throws error if not found
   - Used for updates and deletes

4) update_task(string id, Task new_data)
   - Finds task by ID
   - Updates all fields (title, description, etc.)
   - Keeps same ID and creation date
   - Saves to file
   - Returns true/false for success

5) delete_task(string id)
   - Finds task and removes it from list
   - Saves updated list to file
   - Returns true/false

6) toggle_complete(string id)
   - Finds task
   - If completed=false → sets to true + adds completion timestamp
   - If completed=true → sets to false + clears timestamp
   - Saves to file

7) get_statistics()
   - Loops through all tasks
   - Counts: total, completed, pending
   - Calculates completion rate percentage
   - Returns JSON: {"total": 12, "completed": 3, "pending": 9, ...}

8) get_weekly_stats()
   - Looks at tasks completed in last 7 days
   - Groups by date
   - Returns array: [{"date": "2026-04-05", "count": 3}, ...]
   - Used for bar chart

9) get_category_stats()
   - Counts tasks in each category (Study, Work, Shopping, etc.)
   - Returns: {"study": 5, "work": 3, "shopping": 2, ...}
   - Used for pie chart

10) load_from_file() and save_to_file()
    - Reads/writes data/tasks.json
    - Converts between C++ Task objects and JSON format
    - Creates file if doesn't exist

Header file - defines the structure of a Task and declares all functions.

TASK STRUCTURE:
---------------
struct Task {
    string id;              // Unique identifier: "a8f3d9e2"
    string title;           // Main text: "Buy groceries"
    string description;     // Details: "Milk, eggs, bread"
    string category;        // Group: "shopping"
    string due_date;        // When due: "2026-04-15"
    string due_time;        // Time: "14:30"
    string reminder_time;   // Alert: "2026-04-15T13:30"
    string notes;           // Extra info
    int priority;           // 1=High, 2=Medium, 3=Low
    bool completed;         // true/false
    string completed_at;    // Timestamp when marked done
    string created_at;      // When task was created
};

WHY WE NEED .h FILE:
- In C++, you "declare" functions in .h file
- Then "define" (write actual code) in .cpp file
- This lets other files (like main.cpp) know what functions exist
- Like a menu in a restaurant - lists what's available!

WHAT IT DOES:
Stores all tasks persistently. Like a notebook where we write everything down.

FORMAT:
-------
[
  {
    "id": "a8f3d9e2",
    "title": "Complete C++ assignment",
    "description": "Finish pointers chapter exercises",
    "category": "study",
    "due_date": "2026-04-10",
    "due_time": "23:59",
    "priority": 1,
    "completed": false,
    "created_at": "2026-04-05T10:30:00"
  },
  {
    "id": "b7e2f1a3",
    "title": "Buy groceries",
    "category": "shopping",
    "completed": true,
    "completed_at": "2026-04-06T14:20:00"
  }
]

WHY JSON?
---------
1. Human-readable (you can open and understand it)
2. Easy to parse in both C++ (nlohmann/json library) and JavaScript (native)
3. Standard format for web applications
4. Simple file storage (no database setup needed)

HOW IT WORKS:
-------------
- When server starts: Reads file → Loads into memory (C++ vector)
- When user adds task: Updates memory → Writes entire array back to file
- When user deletes task: Updates memory → Writes to file
- When user marks complete: Updates memory → Writes to file

IMPORTANT: File is created automatically if it doesn't exist!

   - Links required libraries to executable
   - On Windows: adds ws2_32 and mswsock (socket libraries)

6) target_compile_definitions(server PRIVATE ASIO_STANDALONE)
   - Tells ASIO to work without Boost library

PART 7: LIBRARIES & PACKAGES EXPLAINED
================================================================================

┌────────────────────────────────────────────────────────────────────────────┐
│ BACKEND LIBRARIES (C++)                                                    │
└────────────────────────────────────────────────────────────────────────────┘

1. CROW FRAMEWORK
   ──────────────
   What: Lightweight web framework for C++
   Why: Makes building HTTP servers easy
   Without it: Would need to write low-level socket code (very hard!)
   
   What it provides:
   - CROW_ROUTE macro to define endpoints
   - Request/response objects
   - JSON support
   - Automatic routing
   - Multithreading support
   
   Example usage:
   CROW_ROUTE(app, "/hello")
   ([](){
       return "Hello World!";
   });

2. ASIO (Asynchronous I/O)
   ───────────────────────
   What: Networking library
   Why: Handles TCP/IP connections, sockets
   Crow uses: Crow is built on top of ASIO
   
   What it provides:
   - Socket creation and management
   - Asynchronous operations (non-blocking)
   - Cross-platform (works on Windows, Mac, Linux)
   
   We don't directly use ASIO - Crow uses it internally!

3. nlohmann/json
   ─────────────
   What: Modern C++ JSON library
   Why: Makes working with JSON super easy
   
   Without it:
   - Manual string parsing (nightmare!)
   - Prone to errors
   - Lots of code
   
   With it:

KEY INTEGRATION POINTS:

1. SAME ORIGIN = NO CORS ISSUES
   -------------------------------
   Frontend files served from: localhost:8080/
   API endpoints at: localhost:8080/api/
   Same server, same port → Browser allows requests!

2. JSON AS COMMON LANGUAGE
   -------------------------
   C++ speaks: Task objects (struct)
   JavaScript speaks: Objects {title: "...", ...}
   JSON bridges: Both can read/write JSON!

3. HTTP AS COMMUNICATION PROTOCOL
   --------------------------------
   Frontend and backend don't share memory
   They communicate via HTTP requests/responses
   Like two people talking via walkie-talkie!

   -------------------
   GET /api/tasks          → Read all
   POST /api/tasks         → Create
   PUT /api/tasks/:id      → Update
   DELETE /api/tasks/:id   → Delete

Q1: Why did you choose C++ for backend instead of Node.js or Python?
────────────────────────────────────────────────────────────────────
A: We wanted to demonstrate:
   • Systems programming skills (memory management, compilation)
   • Performance (C++ is faster than interpreted languages)
   • Integration of modern C++ with web technologies
   • Use of modern frameworks like Crow that make C++ web dev practical
   
   It shows we can work beyond just scripting languages!

Q2: How does the frontend communicate with backend?
────────────────────────────────────────────────────
A: Via HTTP requests using the Fetch API:
   • Frontend (JavaScript) sends HTTP requests to API endpoints
   • Backend (C++ server) processes requests and sends responses
   • Data format: JSON (works natively in both JavaScript and C++ with library)
   • Same server architecture (port 8080) eliminates CORS issues
   
   Example: fetch('/api/tasks') → C++ CROW_ROUTE → task_service → JSON response

Q3: What happens if server crashes?
────────────────────────────────────
A: All data is preserved because:
   • Tasks stored in tasks.json file on disk
   • Every create/update/delete immediately writes to file
   • When server restarts, TaskService constructor loads from file
   • No data loss!
   
   This is persistent storage vs in-memory only.

Q4: Why JSON file instead of a database?
─────────────────────────────────────────
A: For this project scope:
   • Simpler setup (no database installation/configuration)
   • Demonstrates file I/O operations
   • Sufficient for single-user application
   • JSON is human-readable (easy to debug)
   
   For production with many users: Would use MySQL/PostgreSQL

Q5: Can you explain the build process?
───────────────────────────────────────
A: Three stages:
   1. Configure: cmake -S . -B build
      • Reads CMakeLists.txt
      • Downloads dependencies from GitHub (Crow, ASIO, nlohmann/json)
      • Generates build files
   
   2. Compile: cmake --build build
      • Compiles src/main.cpp and src/task_service.cpp
      • Links libraries
      • Creates executable: build/server.exe
   
   3. Run: build/server.exe
      • Starts HTTP server on port 8080
      • Loads tasks from JSON file
      • Waits for requests

Q6: What are those CROW_ROUTE things?
──────────────────────────────────────
A: Macros provided by Crow framework for defining routes:
   • Route = URL pattern + handler function
   • When request matches URL, handler runs
   
   Example:
   CROW_ROUTE(app, "/api/tasks")
   ([&task_service](const crow::request& req) {
       // This code runs when someone visits /api/tasks
       return task_service.get_all_tasks();
   });
   
   It's like: "When someone knocks on this door (/api/tasks), do this."

Q7: How do you handle errors?
──────────────────────────────
A: Multiple layers:
   • Try-catch blocks in C++ to catch exceptions
   • Validation (e.g., title cannot be empty)
   • HTTP status codes (400 = bad request, 404 = not found, 500 = server error)
   • Frontend checks response status and shows error messages
   
   Example: Missing title → Server returns 400 with JSON {"error": "Title required"}

Q8: What is localhost:8080?
────────────────────────────
A: localhost = 127.0.0.1 = Your own computer (loopback address)
   8080 = Port number (like a door number)
   
   Full URL: http://localhost:8080
   • http:// = Protocol
   • localhost = This computer
   • :8080 = Port (commonly used for development, alternative to 80)
   
   Only accessible from your machine (not on internet)

Q9: How does the calendar know which dates have tasks?
───────────────────────────────────────────────────────
A: JavaScript logic in renderCalendar():
   • Loads all tasks
   • For each task with due_date, extracts the date
   • When rendering calendar, checks if current date matches any task date
   • If match: Adds special CSS class to highlight that day
   • User sees: Days with tasks are visually different (colored dot, etc.)

PART 11: TECHNICAL TERMS GLOSSARY
================================================================================

API (Application Programming Interface)
  → Set of endpoints that frontend calls to communicate with backend
  → Example: /api/tasks is an API endpoint

REST (Representational State Transfer)
  → Architecture style where URLs represent resources
  → HTTP methods (GET, POST, PUT, DELETE) represent actions
  → Example: GET /api/tasks = retrieve tasks

HTTP Methods
  → GET: Retrieve data (read-only)
  → POST: Create new resource
  → PUT: Update existing resource
  → DELETE: Remove resource
  → OPTIONS: Check what methods are allowed (CORS)

JSON (JavaScript Object Notation)
  → Text format for data exchange
  → Example: {"name": "John", "age": 25}
  → Both JavaScript and C++ can read/write it

CORS (Cross-Origin Resource Sharing)
  → Browser security feature
  → Blocks requests between different origins (different domain/port)
  → We avoid it by serving frontend from same server

Endpoint
  → URL path that handles specific request
  → Example: /api/tasks/category/study

Route/Routing
  → Matching URL to handler function
  → Crow does this with CROW_ROUTE macro

Request
  → Message sent from client to server
  → Contains: method, URL, headers, body

Response
  → Message sent from server to client
  → Contains: status code, headers, body (usually JSON)

Status Codes
  → 200 OK: Success
  → 201 Created: Successfully created
  → 400 Bad Request: Client error (invalid data)
  → 404 Not Found: Resource doesn't exist
  → 500 Internal Server Error: Server crashed

Header-Only Library
  → Library that's just .h/.hpp files (no .cpp to compile)
  → Example: Crow, nlohmann/json
  → Advantage: Easier to integrate

Build System
  → Tool that automates compilation process
  → We use CMake
  → Reads CMakeLists.txt, generates Makefiles, compiles code

Dependency Management
  → Handling external libraries
  → CMake's FetchContent downloads from GitHub automatically

Asynchronous
  → Non-blocking operations
  → Server can handle multiple requests at once
  → ASIO provides this capability

Persistent Storage
  → Data that survives program restart
  → We use JSON file
  → Alternative: Database (MySQL, PostgreSQL)
